## 2. 项目背景

当前储蓄记录主要通过手机备忘录手动维护。女朋友为了减少冲动消费，会将一部分储蓄转给保管员代为保管；当她需要用钱时，再向保管员提出取款需求。

现有方式存在几个问题：

1. 余额需要人工计算，容易出错。
2. 存取款记录分散在备忘录和真实转账记录里，不够清晰。
3. 取款申请没有标准流程，容易出现口头沟通遗漏。
4. 储户无法实时查看账户余额和历史流水。
5. 储蓄过程缺少仪式感和正反馈。

因此，希望开发一个两人专用的手机端储蓄系统，让储户可以查看余额、提交取款申请、记录存款；保管员可以审批取款、确认到账、维护流水，并自动计算余额。

---

## 3. 产品定位

StefBank 不是一个真实金融产品，也不接入真实支付或银行接口。它是一个私人情侣储蓄托管系统，本质是：

> 情侣共享的储蓄记账 + 存取款申请 + 审批确认 + 余额可视化工具。

产品气质应区别于企业后台或严肃银行 App，而是偏向：

- 情侣化
- 清新可爱
- 轻银行感
- 有仪式感
- 透明、可追溯
- 操作简单

## 4. 目标用户与角色

### 4.1 储户 depositor

对应女朋友角色。主要诉求：

- 查看当前余额。
- 查看历史存取款记录。
- 提交取款申请。
- 提交存款记录。
- 查看申请审批状态。
- 了解自己本月存取款情况。
- 通过目标进度减少冲动消费。

### 4.2 保管员 manager

对应“车厘子银行行长”。主要诉求：

- 查看账户余额和所有流水。
- 新增存入、取出、修正流水。
- 审批储户提交的取款申请。
- 确认储户提交的存款是否到账。
- 标记取款是否已经实际转账。
- 维护账目准确性。
- 查看统计数据，辅助双方复盘储蓄情况。

## 5. 核心使用场景

### 5.1 储户查看余额

储户打开 StefBank 首页，即可看到当前余额、累计存入、累计取出、本月存入、本月取出、储蓄目标进度等信息。

### 5.2 储户申请取款

储户需要用钱时，在系统里填写取款金额、理由、分类、紧急程度和到账方式。提交后进入待审批状态。保管员审批通过并完成转账后，系统自动生成取款流水并更新余额。

### 5.3 储户提交存款

储户实际转账给保管员后，在系统内提交存款记录。保管员确认到账后，系统生成存款流水并更新余额。

### 5.4 保管员维护流水

保管员可以直接新增存入、取出或修正流水。所有流水应保留操作记录，不建议物理删除。

### 5.5 双方查看历史记录

双方都可以查看完整流水，包括日期、类型、金额、余额、备注、状态等，减少沟通成本和账目争议。

## 7. 功能需求

## 7.1 登录与角色识别

### 功能说明

系统仅供两人使用，需要识别当前用户身份。不同角色看到的按钮和可执行操作不同。

### 用户故事

作为储户，我希望登录后只看到自己需要的功能，例如查看余额、申请取款、提交存款。

作为保管员，我希望登录后能看到审批入口和账目管理入口。

### 功能规则

1. 用户登录后进入首页。
2. 系统根据用户角色展示不同功能入口。
3. 储户不能直接修改余额。
4. 储户不能审批自己的取款申请。
5. 保管员可以处理所有申请和流水。

### MVP 实现建议

第一版可以先用简单账号密码登录，或 Supabase Auth。因为只有两个人使用，也可以先内置两个测试账户：

- depositor@example.com
- manager@example.com

后续再替换为真实邮箱或手机号登录。

## 7.3 流水列表

### 功能说明

展示所有存入、取出、修正记录，替代当前备忘录手动记录方式。

### 字段

每条流水包含：

| 字段 | 说明 |
|---|---|
| 日期 | 交易发生日期 |
| 类型 | 存入 / 取出 / 修正 |
| 金额 | 正数金额，类型决定方向 |
| 余额 | 该笔交易后的余额 |
| 分类 | 购物 / 吃饭 / 学习 / 交通 / 应急 / 其他 |
| 备注 | 用户填写的说明 |
| 状态 | 待确认 / 已确认 / 已驳回 / 已作废 |
| 操作人 | 谁创建了这条记录 |
| 确认人 | 谁确认了这条记录 |

### 列表展示规则

1. 默认按交易日期倒序排列。
2. 存入金额显示为 `+¥xxx`。
3. 取出金额显示为 `-¥xxx`。
4. 修正金额可以为正或负。
5. 已作废流水应弱化显示，但不物理删除。
6. 点击流水可进入详情页。

### 筛选条件

MVP 可先不做复杂筛选。后续支持：

- 按月份筛选。
- 按类型筛选。
- 按分类筛选。
- 按状态筛选。

### 验收标准

1. 所有已确认流水都能正确展示。
2. 每条流水展示交易后余额。
3. 金额正负方向清晰。
4. 移动端列表可顺畅滚动。

## 7.4 新增流水

### 功能说明

保管员可以手动新增流水，用于记录已经发生的存入、取出或修正。

### 页面字段

| 字段 | 类型 | 是否必填 |
|---|---|---|
| 流水类型 | deposit / withdraw / adjustment | 是 |
| 金额 | number | 是 |
| 交易日期 | date | 是 |
| 分类 | select | 否 |
| 备注 | textarea | 否 |

### 业务规则

1. 金额必须大于 0。
2. deposit 增加余额。
3. withdraw 减少余额。
4. adjustment 可增加或减少余额。
5. withdraw 后余额不能小于 0。
6. 新增成功后生成一条 confirmed 状态流水。
7. 新增流水后自动更新账户余额。
8. 每条流水保存 `balance_after`。

### 验收标准

1. 保管员能成功新增存入流水。
2. 保管员能成功新增取出流水。
3. 取出金额超过余额时，应阻止提交并提示余额不足。
4. 新增成功后首页余额即时更新。
5. 流水列表中能看到新增记录。

## 7.5 取款申请

### 功能说明

储户可以主动提交取款申请，由保管员审批。

### 页面字段

| 字段 | 类型 | 是否必填 | 示例 |
|---|---|---|---|
| 取款金额 | number | 是 | 500 |
| 取款理由 | textarea | 是 | 买衣服 |
| 分类 | select | 否 | 购物 |
| 紧急程度 | select | 是 | 普通 / 今天要 / 救命啊 |
| 到账方式 | select | 是 | 微信 / 支付宝 / 银行卡 / 现金 |
| 备注 | textarea | 否 | 晚上之前需要 |

### 申请状态

| 状态 | 说明 |
|---|---|
| pending | 待审批 |
| approved | 已批准，待转账 |
| rejected | 已驳回 |
| completed | 已完成，已生成流水 |

### 用户故事

作为储户，我希望可以提交取款申请，而不是每次都靠聊天记录沟通。

作为保管员，我希望可以看到申请理由和金额，并决定是否批准。

### 业务规则

1. 取款金额必须大于 0。
2. 申请金额不能超过当前余额。
3. 储户提交后状态为 pending。
4. 保管员可以批准或驳回。
5. 批准后状态变为 approved。
6. 保管员完成实际转账后，点击“标记已转账”。
7. 标记完成后状态变为 completed。
8. 系统自动生成 withdraw 流水。
9. 流水生成后自动更新余额。
10. 已完成申请不可重复生成流水。

### 验收标准

1. 储户可以提交取款申请。
2. 保管员可以在审批后台看到该申请。
3. 保管员批准后，申请状态正确变化。
4. 保管员标记已转账后，系统生成取款流水。
5. 首页余额减少对应金额。
6. 重复点击完成不会重复扣款。

## 9. 数据模型

## 9.1 users 用户表

```sql
create table users (
  id uuid primary key default gen_random_uuid(),
  email text unique,
  name text not null,
  role text not null check (role in ('depositor', 'manager')),
  avatar_url text,
  created_at timestamp with time zone default now()
);
```

## 9.2 accounts 账户表

```sql
create table accounts (
  id uuid primary key default gen_random_uuid(),
  name text not null default 'StefBank',
  display_name text default '车厘子银行存款系统',
  current_balance numeric(12, 2) not null default 0,
  target_amount numeric(12, 2),
  created_at timestamp with time zone default now(),
  updated_at timestamp with time zone default now()
);
```

## 9.3 transactions 流水表

```sql
create table transactions (
  id uuid primary key default gen_random_uuid(),
  account_id uuid references accounts(id),
  type text not null check (type in ('deposit', 'withdraw', 'adjustment')),
  amount numeric(12, 2) not null check (amount > 0),
  direction text not null check (direction in ('in', 'out')),
  balance_after numeric(12, 2) not null,
  description text,
  category text,
  status text not null default 'confirmed' check (status in ('pending', 'confirmed', 'rejected', 'voided')),
  created_by uuid references users(id),
  confirmed_by uuid references users(id),
  transaction_date date not null,
  created_at timestamp with time zone default now(),
  updated_at timestamp with time zone default now()
);
```

## 9.4 requests 申请表

```sql
create table requests (
  id uuid primary key default gen_random_uuid(),
  account_id uuid references accounts(id),
  request_type text not null check (request_type in ('deposit', 'withdraw')),
  amount numeric(12, 2) not null check (amount > 0),
  reason text,
  category text,
  urgency text check (urgency in ('normal', 'today', 'emergency')),
  payment_method text,
  status text not null default 'pending' check (status in ('pending', 'approved', 'rejected', 'completed')),
  requested_by uuid references users(id),
  reviewed_by uuid references users(id),
  review_note text,
  related_transaction_id uuid references transactions(id),
  created_at timestamp with time zone default now(),
  reviewed_at timestamp with time zone,
  completed_at timestamp with time zone
);
```

## 9.5 goals 储蓄目标表

```sql
create table goals (
  id uuid primary key default gen_random_uuid(),
```

## 10. 余额计算规则

### 10.1 推荐原则

余额应由 confirmed 流水计算得出。为了提升页面性能，可以在 accounts 表中冗余保存 `current_balance`，但它必须与流水保持一致。

### 10.2 计算逻辑

deposit：

```text
new_balance = current_balance + amount
```

withdraw：

```text
new_balance = current_balance - amount
```

adjustment：

```text
new_balance = current_balance + amount 或 current_balance - amount
```

### 10.3 关键约束

1. 余额不能低于 0。
2. completed 申请只能生成一条流水。
3. 流水创建后应写入 `balance_after`。
4. 不建议直接编辑已确认流水金额。
5. 如需纠错，优先新增 adjustment 修正流水。
6. 已作废流水不参与余额计算。

## 16. 主要流程

## 16.1 取款申请流程

```text
储户提交取款申请
    ↓
系统校验金额是否大于 0
    ↓
系统校验余额是否充足
    ↓
生成 pending 申请
    ↓
保管员查看申请
    ↓
保管员批准或驳回
    ↓
如果驳回：流程结束
    ↓
如果批准：状态变为 approved
    ↓
保管员完成真实转账
    ↓
点击“已打款”
    ↓
系统生成 withdraw 流水
    ↓
系统更新余额
    ↓
申请状态变为 completed
```

## 16.2 存款确认流程

```text
储户完成真实转账
    ↓
储户提交存款记录
    ↓
生成 pending 存款申请
    ↓
保管员确认是否到账
    ↓
如果驳回：流程结束
    ↓
如果确认：系统生成 deposit 流水
    ↓
系统更新余额
    ↓
申请状态变为 completed
```

MVP 可以简化为：

```text
保管员直接新增 deposit 流水
    ↓
系统更新余额
```

## 17. 异常场景

### 17.1 余额不足

当取款金额大于当前余额时，系统不允许提交或审批完成。

提示文案：

```text
余额不足，StefBank 暂时放不了这笔款 🍒
```

### 17.2 重复点击完成

如果保管员多次点击“已打款”，系统必须防止重复生成流水。

处理方式：

1. 判断申请是否已经 completed。
2. 判断是否已有 related_transaction_id。
3. 如果存在，禁止重复执行。

### 17.3 流水记错

不建议直接删除流水。处理方式：

1. 保管员将错误流水标记为 voided。
2. 或新增 adjustment 修正流水。
3. 系统保留操作痕迹。

### 17.4 申请填错金额

如果申请还在 pending 状态，储户可以撤回后重新提交。MVP 可先不做编辑申请。

## 22. 总结

StefBank 的第一版不应追求复杂金融系统，而应优先解决最核心的问题：

1. 余额清楚。
2. 流水准确。
3. 申请有流程。
4. 审批可追溯。
5. 手机端好用。
6. 风格有亲密感。
